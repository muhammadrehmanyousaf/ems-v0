## How a constraint becomes tests

A field declared `allowNull: false` with `STRING(255)` is **four** tests:

| Input | Expected |
|---|---|
| omitted / empty | rejected with a field-specific message |
| 1 character | accepted |
| 255 characters | accepted **and stored whole** — reload and re-read |
| 256 characters | rejected by validation, **never** a 500 |

That last row is not hypothetical: vendor registration returned
`transaction aborted` 500s because a value overran its VARCHAR(255) instead of
being rejected. A crash-hunt sees a 500 and calls it "server error". Research says
what should have happened, so the bug is nameable.

An ENUM field is a **state machine**: every value is a state, and the tests are
which transitions are legal, which are refused, and who is allowed to make them.

# Derived oracles — hand-researched, not extracted

The sections above are extracted mechanically. These were read out of the services
themselves, because the rule that matters is not in the model.

## Booking status — the REAL state machine

`«api»/src/utils/bookingStatusTransition.js`. A forward-only ladder:

```
Pending(0) → Awaiting Payment(1) → Confirmed(2) → Completed(3)
                   Cancelled  ← from any non-Completed status
```

| Rule | Refusal reason | Test |
|---|---|---|
| Forward-only across the ladder | `lower_rank` | Confirmed → Pending must be refused |
| Cancelled is terminal | `cancelled_terminal` | Cancelled → anything must be refused |
| Completed is terminal | `completed_terminal` | Completed → Cancelled refused **unless** `force` (admin refund path) |
| Completed needs milestones closed | `milestones_pending` | Confirmed → Completed with an open blocking milestone must be refused, and report the open count |
| Same status is a no-op | `noop: true` | re-sending the current status must not write a second history row |
| Actor must be known | throws | roles are exactly `customer` · `vendor` · `admin` · `system` · `webhook` |

**Every successful transition writes one `BookingStatusHistories` row.** A status
change with no history row is a defect even when the status itself is right.

### ⚠️ Two contradictory definitions exist

`«api»/src/utils/constants.js` also exports `VALID_STATUS_TRANSITIONS`:

```js
Pending:   [Confirmed, Cancelled]
Confirmed: [Completed, Cancelled]
Completed: []   Cancelled: []
```

It **disagrees** with the live machine — it has no `Awaiting Payment` at all (4
states vs the model's 5), and forbids `Pending → Completed`, which the rank ladder
allows. It is imported into `bookingController.js:31` and **never used**. Logged as
REC-009. Treat `bookingStatusTransition.js` as the only oracle.

## Booking price — computed server-side, in this order

`«api»/src/services/pricingService.js` → `computeVendorPrice`. The client figure is
never trusted; `priced.lines` are described in `bookingCreateService` as "the
trusted numbers".

```
1. package.price × vehicleQuantity
2. + each additionalPackage.price
3. + menu.price
4. if nothing selected → fall back to business.minimumPrice
5. + bundled add-ons   (flat | per_plate × guestCount | percentage_of_total | free)
6. − umbrella/multi-event discount   (applied AFTER add-ons, so the tier % covers total spend)
7. × seasonal surge   (capped by SEASONAL_MAX_MULTIPLIER)
```

### Rejections — every one is a safe negative test

These can be exercised against production **without creating anything**, because a
correct system refuses them before writing. If one succeeds, that *is* the finding.

| Input | Expected refusal |
|---|---|
| unknown `packageId` | `unknown_package` |
| unknown id in `additionalPackageIds` | `unknown_additional_package` |
| unknown `menuId` | `unknown_menu` |
| `vehicleQuantity` < 1, non-numeric, or > max | `invalid_quantity` |
| unknown `businessId` | `business_not_found` |
| add-on that is mandatory or already included | rejected — the picker offers optional only |
| add-on deactivated mid-cart | clean 400, never a silently-applied stale price |

## Payment status — a separate machine

missing** from the constant. Same class of drift as the booking statuses. REC-009.
