# Optimising every page — the method

Companion to `PERFORMANCE-PLAN-2026-09-28.md`, which measured three pages and found the causes. This one is about covering **all 313**, in an order that comes from data rather than from whichever page I happened to open.

The rule this document exists to enforce: **no page gets touched until it has been measured, and no page is called done until it has been measured again.**

**81 routes need a real id** to be visitable, so the sweep resolves ids from the API before it starts. A sweep that silently visits `/vendor/[id]` and records a 404 as "fast" is worse than no sweep.

### What the inventory already says, before any measurement

- **21 public pages are `"use client"` with no ISR.** Among them the seven vendor-profile detail templates — `/venues/[id]`, `/photographers/[id]`, `/catering/[id]`, `/decor/[id]`, `/makeup-artists/[id]`, `/henna-artists/[id]`, `/car-rental/[id]`, 140 lines each. These are the pages Google ranks and customers land on. `/wedding-venues/[city]` next door is ISR with `generateStaticParams` and makes **zero** runtime API calls — the fast pattern already exists in this repo and these never got it.
- **The vendor console has 0 ISR pages out of 82.** Correct — it is all per-user authenticated data. So its wins are different in kind: request count, payload shape, caching in the client, and not re-fetching what the shell already has.
- The biggest client-rendered pages by size: `/sign/[token]` (713 lines), `/search` (650 — now server-driven), `/planning-tools/guest-list` (639), `/planning-tools/timeline` (562), `/planning-tools/budget` (512), `/review/[token]` (414), `/compare-vendors` (416).

## 2. What gets measured, per page

One harness, `scripts/perf/sweep.cjs`, visits every route twice — once cold, once warm — on a **mid-range Android profile (CPU ×4, 4G, 390px)**, because the desktop numbers lie: the homepage read LCP 1.9 s on this laptop and 7.5 s on the phone profile.

Recorded per page:

| metric | why it is on the list |
|---|---|
| API call count | the homepage was making 36; the count is the single best predictor of a slow page here |
| JSON bytes **decompressed** | brotli hides the problem — 455 KB on the wire was 16.7 MB to parse |
| duplicate API URLs | `/notifications/unread-count` fired 4× from four different callers |
| catalog-scale calls (`limit≥100`) | flags any page still pulling a whole list to render a few rows |
| JS transferred + decoded | 1.3–1.4 MB/page today |
| LCP / FCP / TBT / CLS | the user-facing verdict; thresholds 2500 ms / 300 ms / 0.1 |
| longest single task | an 8 s TBT made of 59 tasks is a different fix from one 2.4 s task |
| console + page errors | a page that logs errors is not "done" however fast it is |
| HTTP status of every request | catches 404/500 hidden behind a spinner |

Vendor-console and customer pages are swept **with a real login**, since an authed page measured while logged out is a redirect measured very fast.

### Guards against the harness lying to me

This is written down because my own instruments have now misled me five times in this session: `getEntriesByType("longtask")` returning nothing without a buffered observer; V8 coverage reading "100 % used" from nested ranges; `.v-amt` text gluing a percentage onto a rupee amount; a card-link selector finding 0 links on a page with 12 cards; typing "marquee" into the field labelled "Which city?".

So the sweep asserts its own sanity and voids the run if any of these trip:
1. **Observers registered via `addInitScript`**, never `getEntriesByType` after load.
2. **A known-good control page** must come in under threshold. If the control is slow, the machine or network is the problem, not the page.
3. **Rendered-content check per page** — a page recorded as "0 API calls, fast" must also prove it rendered something (headings, images, or a non-trivial text length). Blank pages are fast.
4. **Byte sizes from Playwright**, not from the page's `PerformanceResourceTiming` (cross-origin hides `transferSize` without `Timing-Allow-Origin`).
5. **Battery/energy-saver check** — a throttled CPU on a draining battery makes every threshold unjudgeable.
6. Every run writes `sweep-<timestamp>.json` so before/after is a diff, not a memory.

## 3. Ranking: what gets fixed first

Ranked by `impact = cost × reach`, not by cost alone. A 6-second admin page three people open monthly loses to a 2-second page every visitor hits.

**Reach tiers** (highest first):
1. `/` and `/search` — every visitor.
2. The seven vendor-detail templates and the city/type landing pages — every SEO arrival.
3. Vendor console daily screens — `/dashboard`, `/bookings`, `/calendar`, `/leads`, `/money`. One vendor, many hours.
4. Customer booking flow — fewer users, but this is the revenue path, so correctness outranks speed here.
5. Everything else — planning tools, admin, staff.

**Cost** is taken from the sweep, weighted: TBT and API-call count first (they are what makes a page feel broken), then LCP, then bytes.

The output is one table, worst first, with the specific cause named per page — not "optimise /search" but "`/search` makes 17 catalog calls because it filters client-side".

## 4. The fix patterns, and which to reach for

Nearly every page will fall into one of six buckets. Naming them up front stops each page becoming a fresh invention.

| pattern | when it applies | what to do |
|---|---|---|
| **P1 — server-side filter + page** | a page downloads a list to filter or count it in JS | pass the filters the server has; take 12–24 rows; get counts from the DB. *Done for `/search` and the hero.* |
| **P2 — list projection** | a list response carries fields no card renders | `?view=card`. *Done: 743 KB → 113 KB for 200 rows.* |
| **P3 — ISR/static** | a public page whose data is the same for everyone | `revalidate` + `generateStaticParams`, like `/wedding-venues/[city]`. **The seven vendor-detail templates are the big open one.** |
| **P4 — one query, one cache** | several components fetch the same thing independently | one `useQuery` key, or read from the context that already has it. *Open: `unread-count` ×4; 114 raw `useEffect` fetches.* |
| **P5 — composite endpoint** | a screen makes N calls to render one view | one endpoint that resolves them server-side. *Open: the dashboard's 5 analytics calls.* |
| **P6 — defer the third party** | a script competes with the page's own hydration | load on interaction/idle. *Done for GA: bounded at −1,371 ms TBT on the venue page, −2,710 ms on home.* |

Anything that fits none of these gets written up before it gets changed.

## 5. Order of work

Each step ends with a re-sweep of the pages it touched and a commit carrying the before/after numbers.

- **Step 0 — land what is already built and verified.** The card projection, facets, server-side search, the hero, the GA deferral. Backend first (the frontend now depends on `?view=card` and `/businesses/facets`), then re-point `.env.local`, then the frontend. *This is where I am.*
- **Step 1 — build and validate the sweep**, including its self-checks, against the three pages already measured by hand. If the sweep disagrees with the hand measurement, the sweep is wrong and gets fixed before it is trusted on 310 pages.
- **Step 2 — full sweep, ranked table published** into this file. No fixes in this step.
- **Step 3 — public surface, in rank order.** Expected to be dominated by P3 (the seven vendor-detail templates) and P1 leftovers.
- **Step 4 — vendor console, in rank order.** Expected P4 and P5.
- **Step 5 — customer flow.** Correctness gates before speed: the booking path is not allowed to get faster and wronger.
- **Step 6 — planning tools, admin, staff.** Cheap, low reach, done last.
- **Step 7 — gate it.** A per-surface budget (LCP/TBT/JS bytes/API count) enforced in CI, shaped like the TypeScript ratchet that now gates this repo: a number that can only go down. Plus the payload-size assertion in the API tests.

---

## 6. Definition of done, per page

A page is done when all of these hold on the mid-range Android profile:

- LCP < 2,500 ms, TBT < 300 ms, CLS < 0.1
- no duplicate API URL in a single load
- no call returning ≥100 rows to render fewer than 20
- zero console errors, zero non-2xx requests
- it rendered — asserted, not assumed
- the numbers are in a committed sweep file, next to the previous ones

---

## 7. What this plan will not do

- **Not optimise a page nobody uses** to make a table look complete.
- **Not chase a metric at the cost of behaviour.** `/search` moving server-side changed the category filter's semantics; that was written down and flagged, not buried.
- **Not add infrastructure before exhausting shape.** Redis, a search engine and read replicas stay in the other document's later phases; at 3,354 rows and a 6.4 ms query they would be decoration.
- **Not trust one run.** Every number gets a second run before it goes in a commit message.
